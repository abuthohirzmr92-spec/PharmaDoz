# WHAT WENT WELL

## 1. Incremental Engineering Gate

Setiap task diisolasi dengan gate sendiri. Task 1 harus complete + review + approve sebelum Task 2 dimulai. Ini menghilangkan risiko "big bang merge" di akhir sprint.

**Bukti**: 50/50 test PASS setelah setiap task, bukan hanya di akhir sprint. Tidak ada momen "semuanya broken, harus debug 3 jam".

**Dampak**: Confidence tinggi di setiap langkah. Rollback risk minimal.

---

## 2. Behavior Preservation Principle

Prinsip "behavior MUST remain identical" ditegakkan di setiap task. Bukan hanya diuji — didokumentasikan dalam Behavior Preservation Report.

**Bukti**: Regression Matrix 16 fitur, semuanya PASS. Tidak ada bug yang ditemukan di checkout flow setelah refactor.

**Dampak**: Refactor arsitektur tanpa mengubah perilaku = zero user impact. Customer tidak tahu ada perubahan.

---

## 3. Architecture Compliance by Construction

AllocationDraft didesain agar secara type-level TIDAK BISA menyimpan sellingPrice. Bukan hanya "jangan lupa" — tapi "compiler akan menolak".

**Bukti**: `AllocationEntry` type hanya memiliki `batchId`, `allocatedQty`, `allocationOrder`. Tidak bisa menambah `sellingPrice` tanpa mengubah type definition — yang akan melanggar ADR-002.

**Dampak**: Invariant ditegakkan oleh TypeScript compiler, bukan oleh memory developer.

---

## 4. Dual-Write Pattern

Old path dan new path berjalan paralel. Ini adalah insurance policy yang membuat setiap task aman untuk dideploy kapan saja.

**Bukti**: `allocationDraft` (canonical) dan `allocationSnapshot` (legacy) keduanya dipopulasi di CartItem. Consumer bisa baca salah satu. Tidak ada yang broken.

**Dampak**: Sprint V10.2 bisa dideploy ke production secara independen tanpa menunggu V10.3 dan V10.4.

---

## 5. Grep as Architecture Gate

Setiap akhir task, architecture compliance diverifikasi dengan `grep` sederhana: "apakah ada import inventory-store dari hook?"

**Bukti**: CV-1 diverifikasi dalam 1 detik dengan `grep "inventory-store" src/hooks/use-demo-cashier.ts`.

**Dampak**: Tidak ada "violation yang terlewat". Grep memberikan jawaban binary — ya atau tidak.

---

## 6. Documentation Discipline

Setiap fase menghasilkan dokumen yang bisa dibaca secara independen:
- Blueprint (architecture)
- Engineering Plan (planning)
- Implementation Reports (per task)
- Closure (summary)
- Retrospective (ini)

**Bukti**: 5 dokumen terstruktur dalam `docs/architecture/` dan `docs/engineering/`.

**Dampak**: Developer baru bisa onboard dengan membaca dokumen secara berurutan. Tidak perlu "tanya senior".

# CHALLENGES

## 1. Pre-Existing Test Failures

16 test dari sprint sebelumnya (inventory-store, rbac, unit-converter) gagal sebelum V10.2 dimulai. Ini menimbulkan noise saat validasi.

**Dampak**: Harus selalu memisahkan "test yang gagal karena perubahan saya" vs "test yang memang sudah gagal". Solusi saat ini: run hanya test yang relevan (`cashier-store`, `allocation-builder`, `integration-v10`).

**Resolusi**: Pre-existing failures harus diperbaiki sebelum Sprint V10.3 untuk menghindari akumulasi noise.

---

## 2. Task Dependency Bottleneck

Task 2 bergantung pada Task 1. Task 3 bergantung pada Task 2. Dengan 1 developer, ini unavoidable. Tapi jika tim bertambah, dependency ini akan menjadi bottleneck.

**Dampak**: Critical path adalah sequential — tidak bisa dikerjakan paralel.

**Resolusi**: Untuk sprint dengan multiple developers, pertimbangkan memecah story menjadi unit yang lebih independen. Atau gunakan feature flag agar developer kedua bisa mulai tanpa menunggu.

---

## 3. Legacy Snapshot Maintenance

Hook masih membangun `allocationSnapshot` (legacy) secara manual dari batch data. Ini adalah temporary code yang harus di-maintain sampai V10.3.

**Dampak**: Dual-write berarti dua kali kode untuk membangun data yang sama. Ada risiko drift jika salah satu path berubah.

**Resolusi**: Integration test (Task 4) membandingkan kedua path. V10.3 harus menghapus legacy snapshot building secepat mungkin.

---

## 4. Scope Creep Temptation

Beberapa kali muncul godaan: "sambil mengerjakan Task 2, sekalian perbaiki X". Blueprint dan Engineering Plan menjadi rem yang efektif.

**Dampak**: Tanpa Blueprint yang LOCKED, Sprint V10.2 bisa melebar menjadi "refactor semuanya".

**Resolusi**: Setiap scope creep ditolak dengan merujuk ke Blueprint. "Itu sprint berikutnya."

# DECISIONS THAT WORKED

## 1. Architecture First, Implementation Later

```
Blueprint (V10.1) → Planning → Implementation (V10.2)

Bukan: langsung coding sambil mendesain.
```

**Mengapa berhasil**: Ketika implementasi dimulai, semua keputusan arsitektur sudah dibuat. Developer tidak perlu mikir "bagaimana strukturnya?" — hanya "bagaimana implementasinya?".

**Rekomendasi**: Teruskan untuk semua sprint.

---

## 2. Task Isolation

Setiap task adalah unit kerja independen yang menghasilkan deliverables konkrit.

**Mengapa berhasil**: Task 1 menghasilkan AllocationBuilder yang bisa di-test sendiri tanpa menunggu Task 2. Task 2 menghasilkan hook refactor yang bisa diverifikasi sendiri.

**Rekomendasi**: Pertahankan granularity ini untuk V10.3.

---

## 3. Behavior Preservation Report

Setiap task mendokumentasikan "apa yang TIDAK berubah" — bukan hanya "apa yang berubah".

**Mengapa berhasil**: Reviewer bisa langsung melihat: "Checkout tetap jalan? UI tetap sama? Database tidak berubah?" — semua dijawab di laporan.

**Rekomendasi**: Jadikan template standar untuk semua implementation report.

---

## 4. @deprecated with Removal Sprint

Setiap field legacy ditandai dengan `@deprecated` DAN sprint target removal.

**Mengapa berhasil**: Developer yang membaca kode 3 bulan kemudian tahu persis kapan field ini akan dihapus. Bukan "mungkin suatu hari nanti".

**Rekomendasi**: Standarisasi format: `@deprecated Planned removal: Sprint VXX`.

---

## 5. Integration Test as Capstone

Task 4 tidak membuat fitur baru — hanya membuktikan bahwa Task 1-3 bekerja bersama.

**Mengapa berhasil**: Integration test menemukan 1 bug (FEFO allocation order test yang salah ekspektasi). Tanpa integration test, bug ini mungkin baru ditemukan saat manual testing.

**Rekomendasi**: Setiap sprint harus memiliki integration validation task.

# IMPROVEMENT OPPORTUNITIES

## 1. Automated Architecture Compliance

Saat ini architecture compliance dicek manual dengan `grep`. Ini rawan human error (lupa menjalankan grep, atau salah pattern).

**Usulan**: Tambahkan ESLint rules atau custom script yang memeriksa dependency rules secara otomatis. Misalnya: `no-restricted-imports` untuk memblokir import `@/store/inventory-store` dari `@/hooks/*`.

**Target**: V10.3 Planning.

---

## 2. Test Coverage Gap pada Legacy Snapshot

Hook masih membangun `allocationSnapshot` (legacy) secara manual. Kode ini tidak memiliki dedicated test — hanya tercover oleh integration test secara tidak langsung.

**Usulan**: Tambahkan unit test untuk legacy snapshot building logic. Atau, jika V10.3 akan menghapusnya, skip.

**Target**: Evaluasi saat V10.3 Planning.

---

## 3. Pre-Existing Test Remediation

16 pre-existing failures menimbulkan noise. Sprint V10.3 akan menambah lebih banyak test — noise akan semakin besar.

**Usulan**: Alokasikan waktu di awal V10.3 untuk memperbaiki pre-existing failures. Minimal: inventory-store tests.

**Target**: Awal Sprint V10.3.

---

## 4. BatchProvider Implementation

`BatchProvider` interface sudah didefinisikan di Domain Layer tapi belum diimplementasikan. Hook menerima `ProductBatch[]` langsung.

**Usulan**: Buat `InventoryBatchProvider` adapter yang mengimplementasi `BatchProvider` menggunakan `inventoryRepo` yang existing.

**Target**: Sprint V10.4 (sebelum CheckoutSessionService).

---

## 5. Pipeline Automation

Saat ini setiap task divalidasi manual: run `tsc`, run `vitest`, run `grep`, check build. Ini seharusnya otomatis.

**Usulan**: Setup pre-commit hook atau CI pipeline yang menjalankan: TypeScript → Tests → Architecture grep checks.

**Target**: V10.3 Planning.
