## 1.3 Critical Code Paths

### Path A: Add To Cart (`use-demo-cashier.ts:193-253`)
```
addDemoProductToCart:
  1. Compute baseQty via UUCE (toBaseUnit)
  2. Access inventoryStore (Zustand) — getState()
  3. Filter batches by productId
  4. Call allocateFefo() — FEFO engine
  5. Build AllocationSnapshot with sellingPrice ← VIOLATION
  6. Extract price from snapshot
  7. Create CartItem with mixed concerns
  8. Call store.addToCart()
```

### Path B: Finalize Transaction (`cashier-store.ts:187-371`)
```
finalizeTransaction:
  1. Validate cart not empty
  2. Compute subtotal (cart items × unitPrice)
  3. Validate payment ≥ subtotal
  4. Duplicate prevention (cart hash)
  5. Build Transaction object
  6. Persist to Supabase (transactionRepo)
  7. Call invStore.deductForSale() ← GOD STORE call
  8. deductForSale → allocateFefo → applySaleDeduction
  9. Record stock movements
  10. Record sale_batch_allocations (HPP)
  11. Add to transaction store
  12. Offline sync enqueue
```

### Path C: Checkout Flow
```
UI click "Bayar" → openPaymentModal
  → PaymentModal → addPayment()
  → finalizeTransaction() ← single monolithic call
    → All allocation + pricing + persistence in ONE call
```

# FASE 8: ALLOCATION DOMAIN DESIGN

## 8.1 AllocationDraft — What it IS

```
AllocationDraft IS:
  ✓ A mutable draft of which batches supply a cart item
  ✓ Generated by FEFO engine
  ✓ Can be rebuilt (quantity change, unit change, time elapsed)
  ✓ Pure batch allocation — which batch, how many units

AllocationDraft IS NOT:
  ✗ A transaction
  ✗ A price calculator
  ✗ A discount engine
  ✗ Permanent (it's a draft until frozen)
  ✗ Visible outside CheckoutSession
```

## 8.2 FEFO Engine — Unchanged, Just Relocated

The FEFO engine itself (`allocateFefo()`) is already a PURE FUNCTION in `inventory-demo.ts`. The issue is not the engine — it's WHERE it's called from.

```
CURRENT:  use-demo-cashier.ts → inventoryStore.allocateFefo()
TARGET:   AllocationBuilder → FEFO engine (pure import)
                               ↓
                          Inventory Repository
                          (provides batches[])
```

## 13.2 Top 3 Critical Risks

- **Scenario**: PricingEngine produces different grandTotal than current inline calculation
- **Impact**: Charging customer wrong amount — financial loss
- **Mitigation**: 
  - PricingEngine must produce IDENTICAL output to current logic
  - Write comparison tests: `expect(newPricing).toEqual(oldPricing)` for 100+ scenarios

- **Scenario**: "While we're refactoring, let's also fix X, Y, Z"
- **Impact**: Scope creep → missed deadline → broken checkout
- **Mitigation**:
  - STRICT scope freeze per sprint
  - Any scope change requires new Architecture Review
  - "One domain extraction per sprint" rule

### CRITICAL #3: Test Coverage Gap (R10)
- **Scenario**: New code paths not tested, old paths removed too early
- **Impact**: Regression bugs in checkout
- **Mitigation**:
  - 100% test coverage on AllocationBuilder, PricingEngine

```
ADR-V10.1-001: CHECKOUT SESSION AS AGGREGATE ROOT
  Status: Accepted (2026-07-05, Architecture Governance v1.0)
  Decision: Introduce CheckoutSession as the single aggregate root
            for the checkout flow, replacing the current ad-hoc
            cart → inventory → transaction pipeline.
  Rationale:
    1. Single source of truth for checkout state
    2. Clear lifecycle (DRAFT → FROZEN)
    3. Enforces dependency rules (Cart does NOT know Inventory)
    4. Enables lazy allocation (allocate only on checkout, not on add-to-cart)
  Consequences:
    - New domain type: CheckoutSession
    - New service: CheckoutSessionService
    - Existing store must delegate to service

ADR-V10.1-002: SEPARATE ALLOCATION FROM PRICING
  Status: Accepted (2026-07-05, Architecture Governance v1.0)
  Decision: AllocationDraft (batch allocation only) and PriceSnapshot
            (pricing only) are separate value objects.
  Rationale:
    1. Allocation can change without price changes (quantity update)
    2. Price can change without allocation changes (promotion applied)
    3. Current AllocationSnapshot violates SRP by carrying sellingPrice
  Consequences:
    - Must split current AllocationSnapshot into two objects
    - PricingEngine becomes standalone domain service
    - AllocationBuilder no longer imports Money Policy

ADR-V10.1-003: EVOLUTIONARY MIGRATION ONLY
  Status: Accepted
  Decision: All changes follow evolutionary (strangler fig) pattern.
            No Big Bang refactor.
  Rationale:
    1. Checkout is critical path — must never break
    2. Dual-write allows parallel validation
    3. Legacy removal only after new path proven stable
  Consequences:
    - Migration takes 4 sprints (V10.1–V10.4)
    - Legacy code coexists temporarily
    - Slightly higher maintenance during migration

ADR-V10.1-004: DOMAIN SERVICES ARE STATELESS PURE FUNCTIONS
  Status: Accepted (2026-07-05, Architecture Governance v1.0)
  Decision: AllocationBuilder, PricingEngine, AllocationValidator,

  Rationale:
    1. Testable without mocking Zustand
    2. No hidden side effects
```

## ADR-001: CheckoutSession sebagai Aggregate Root

### Status
**ACCEPTED** — Approved by Architecture Board + Product Owner, 2026-07-05. Architecture Governance v1.0.

### Context
Saat ini (V9), checkout flow tidak memiliki aggregate root. Cart (Zustand store) menyimpan item, hook (`use-demo-cashier`) membangun allocation snapshot, dan `cashier-store.finalizeTransaction()` menangani semuanya secara monolitik. Tidak ada single entry point untuk operasi checkout.

### Problem
1. **No single source of truth** — Cart, Allocation, Pricing, dan Transaction tersebar di 3 file berbeda
2. **No lifecycle** — Tidak ada status formal untuk progress checkout (draft → allocated → priced → validated → frozen)
3. **No consistency boundary** — Perubahan di satu bagian tidak dijamin konsisten dengan bagian lain
4. **Direct cross-boundary access** — Hook mengakses Inventory Store langsung untuk FEFO

### Decision
**CheckoutSession menjadi Aggregate Root untuk seluruh checkout flow.**

```
CheckoutSession (Aggregate Root)
├── sessionId: UUID
├── cartId: FK → Cart
├── status: DRAFT → ALLOCATING → PRICED → VALIDATED → FROZEN → CANCELLED
├── version: number (optimistic concurrency)
│
├── allocationDraft?: AllocationDraft       ← Value Object (child)
├── priceSnapshot?: PriceSnapshot           ← Value Object (child)
├── validationResult?: ValidationResult     ← Value Object (child)
└── transactionSnapshot?: TransactionSnapshot ← Value Object (child, immutable after freeze)
```

Semua perubahan pada checkout harus melalui CheckoutSession. Tidak boleh ada akses langsung ke Allocation, Pricing, atau Validation dari luar Aggregate.

### Alternatives Considered

| Alternative | Description | Verdict |
|-------------|-------------|---------|
| **A: Tetap tanpa Aggregate Root (current)** | Cart tetap sebagai plain array, allocation sebagai field di CartItem | **Rejected** — Sudah terbukti bermasalah (V9 coupling issues) |
| **B: Transaction sebagai Aggregate Root** | Transaction (yang sudah ada) diperluas untuk menangani seluruh flow | **Rejected** — Transaction adalah hasil akhir, bukan proses. Transaction harus immutable |
| **C: Cart sebagai Aggregate Root** | Cart (Zustand store) menjadi aggregate root | **Rejected** — Cart adalah UI state. Aggregate Root tidak boleh UI state |
| **D: CheckoutSession sebagai Aggregate Root** | Objek baru khusus untuk mengelola lifecycle checkout | **Selected** |

### Rejected Alternatives — Detail

**Rejected A (No Aggregate Root):**
- Alasan ditolak: Tanpa aggregate root, tidak ada consistency boundary. Cart bisa berubah tanpa allocation ikut berubah. Pricing bisa dihitung dua kali dengan hasil berbeda.
- Konsekuensi jika dipilih: Lanjut dengan masalah coupling yang sama, sulit di-test, sulit di-extend.

**Rejected B (Transaction as AR):**
- Alasan ditolak: Transaction adalah immutable snapshot hasil checkout. Memaksanya menjadi mutable selama proses checkout melanggar prinsip dasarnya. Sejak Freeze, Transaction tidak boleh berubah.
- Konsekuensi jika dipilih: Transaction menjadi God Object — mutable sebelum freeze, immutable setelahnya. Dua perilaku dalam satu type.

**Rejected C (Cart as AR):**
- Alasan ditolak: Cart adalah UI state murni. Menjadikannya AR berarti UI state mengelola domain logic. Ini melanggar Clean Architecture.
- Konsekuensi jika dipilih: Cart Store menjadi God Store seperti sekarang, menggabungkan UI concern dan domain concern.

### Consequences

**Positive:**
1. Single entry point untuk seluruh checkout flow
2. Lifecycle eksplisit — mudah di-track, mudah di-debug
3. Consistency boundary — perubahan allocation selalu diikuti pricing ulang
4. Testable — CheckoutSession bisa di-test tanpa UI
5. Extensible — menambah state baru (misal: `AWAITING_APPROVAL` untuk resep) tinggal tambah enum

**Negative:**
1. Tambahan kompleksitas — satu objek baru dengan lifecycle 6 state
2. Migration cost — perlu memisahkan logic dari store ke service
3. Learning curve — developer baru harus paham lifecycle CheckoutSession

**Mitigation:**
- CheckoutSessionService sebagai facade — menyembunyikan kompleksitas lifecycle
- Dokumentasi sequence diagram (sudah ada di FASE 15)
- Dual-write selama migrasi (V10.2–V10.4)

## ADR-002: Allocation Dipisahkan dari Pricing

### Status
**ACCEPTED** — Approved by Architecture Board + Product Owner, 2026-07-05. Architecture Governance v1.0.

### Context
Saat ini (V9), `AllocationSnapshot` (di `cashier-store.ts`) menyimpan data campuran:
```typescript
interface AllocationSnapshot {
  batchId: string;
  batchNumber: string;
  sellingPrice: number;      // ← PRICING CONCERN
  allocatedQuantity: number;  // ← ALLOCATION CONCERN
  expiredDate: string;        // ← BATCH CONCERN
}
```

Tiga concern berbeda dalam satu interface. Ini adalah **Single Responsibility Principle violation**.

### Problem

**Allocation (alokasi stok) dan Pricing (perhitungan harga) adalah dua domain yang BERBEDA:**

| Allocation Domain | Pricing Domain |
|-------------------|----------------|
| FEFO-based batch selection | Selling price per batch |
| Quantity distribution | Discount rules |
| Stock sufficiency check | Tax computation |
| Batch expiry check | Promotion application |
| Allocation order (priority) | Margin calculation |

Ketika digabung:
1. Perubahan harga (promo, diskon) memaksa rebuild allocation — padahal allocation tidak berubah
2. Perubahan quantity memaksa kalkulasi harga ulang — padahal harga satuan tidak berubah
3. Allocation tidak bisa di-refresh tanpa membawa harga
4. Pricing rules tidak bisa di-test secara independen dari allocation

**Mengapa Allocation TIDAK BOLEH mengetahui Selling Price, Discount, Tax, Promotion, Margin:**

1. **Selling Price**: Harga jual adalah keputusan bisnis yang bisa berubah kapan saja (promo, diskon member). Allocation murni tentang "batch mana yang stoknya diambil" — tidak peduli berapa harga jualnya.

2. **Discount**: Diskon adalah aturan bisnis yang bergantung pada customer, member tier, promo code. Allocation tidak punya konteks customer.

3. **Tax**: Pajak (PPN, PPh) bergantung pada kategori produk (obat bebas vs keras) dan aturan pemerintah. Allocation tidak peduli pajak.

4. **Promotion**: Promo bisa berubah-ubah (flash sale, bundling). Allocation tidak boleh terpengaruh.

5. **Margin**: Margin = sellingPrice - costPrice. Allocation harus tahu costPrice (HPP)? Tidak. CostPrice adalah data batch, bukan hasil kalkulasi allocation.

### Decision
**AllocationDraft dan PriceSnapshot adalah dua Value Object yang SEPARATE.**

```
AllocationDraft (V10)           PriceSnapshot (V10)
├── draftId                     ├── snapshotId
├── entries: [{                 ├── entries: [{
│     batchId                   │     batchId
│     allocatedQty              │     batchNumber
│     allocationOrder           │     sellingPrice    ✓ PRICE HERE
│   }]                          │     costPrice       ✓ COST HERE
├── totalAllocated              │     allocatedQty
└── generatedAt                 │     subtotal
                                │   }]
                                ├── subtotal
                                ├── discount
                                ├── tax
                                ├── promotion
                                ├── grandTotal
                                └── generatedAt
```

### Alternatives Considered

| Alternative | Description | Verdict |
|-------------|-------------|---------|
| **A: Tetap gabung (current)** | AllocationSnapshot dengan sellingPrice | **Rejected** — SRP violation, coupling |
| **B: Allocation dengan optional price** | sellingPrice jadi optional field | **Rejected** — Tetap campur, hanya disembunyikan |
| **C: Price sebagai derived field** | Price dihitung dari batch lookup setiap kali dibutuhkan | **Rejected** — Non-deterministic; batch price bisa berubah antara lookup |
| **D: Allocation dan Pricing terpisah** | Dua value object independent | **Selected** |

### Rejected Alternatives — Detail

**Rejected A (Tetap Gabung):**
- Alasan ditolak: V9 sudah menunjukkan masalah — allocation harus di-rebuild saat harga promo berubah
- Konsekuensi: Lanjut dengan SRP violation, sulit menambah pricing rules baru

**Rejected B (Optional Price):**
- Alasan ditolak: Tidak menyelesaikan masalah fundamental. Tetap satu object dengan dua concern
- Konsekuensi: IF statement dimana-mana — "if price exists, use it; else lookup"

**Rejected C (Derived Field):**
- Alasan ditolak: Price lookup non-deterministic. Batch price bisa berubah antara waktu allocation dan waktu pembacaan
- Konsekuensi: Harga di receipt bisa berbeda dengan harga saat checkout

### Consequences

**Positive:**
1. Allocation bisa di-refresh tanpa mempengaruhi harga
2. Pricing rules bisa di-test secara independen
3. Promo/discount bisa ditambahkan tanpa menyentuh allocation
4. Setiap domain punya interface minimal (Interface Segregation)
5. PriceSnapshot bisa di-snapshot pada waktu tertentu (point-in-time pricing)

**Negative:**
1. Dua objek yang sebelumnya satu — lebih banyak alokasi memori (minor)
2. Harus menjaga konsistensi antara allocation dan pricing (dijamin oleh CheckoutSession)
3. Migration: AllocationSnapshot harus di-split

**Mitigation:**
- CheckoutSession memastikan: setiap perubahan AllocationDraft selalu diikuti PricingEngine.calculate()
- Event-driven: AllocationBuilt → PricingEngine otomatis
- Test: `allocationDraft.totalAllocated === priceSnapshot.totalAllocatedQty`

## ADR-003: FEFO Tetap Pure Domain Service

### Status
**ACCEPTED** — Tidak perlu perubahan. FEFO sudah pure.

### Context
FEFO (First Expired, First Out) engine saat ini sudah merupakan pure function di `src/lib/inventory-demo.ts`:

```typescript
export function allocateFefo(
  batches: ProductBatch[],
  productId: string,
  neededQty: number,
): FefoAllocation[]
```

FEFO menerima `batches[]` dan mengembalikan `FefoAllocation[]`. Tidak ada side effect. Tidak ada akses store. Tidak ada akses database.

### Problem
Meskipun FEFO sudah pure, **PEMANGGILNYA yang bermasalah**:
- `use-demo-cashier.ts` memanggil `allocateFefo()` langsung
- `cashier-store.ts` tidak langsung memanggil, tapi lewat `inventoryStore.allocateFefo()`

Ini bukan masalah FEFO, tapi masalah DI MANA FEFO dipanggil.

### Decision
**FEFO tetap menjadi pure domain service. FEFO hanya menerima `Batch[]` dan menghasilkan `Allocation[]`.**

**FEFO TIDAK BOLEH mengetahui:**
- ❌ React — tidak boleh import dari `react`
- ❌ Zustand — tidak boleh import dari `zustand` atau store manapun
- ❌ Database — tidak boleh query Supabase/Postgres
- ❌ Repository — tidak boleh import dari `@/lib/repositories/`
- ❌ API — tidak boleh fetch/axios
- ❌ UI — tidak boleh JSX, component, hook
- ❌ Cart — tidak boleh tahu CartItem, CartStore
- ❌ CheckoutSession — tidak boleh tahu session lifecycle
- ❌ Pricing — tidak boleh menghitung harga
- ❌ Receipt — tidak boleh format untuk tampilan

**FEFO HANYA:**
- ✅ Menerima `ProductBatch[]` (array batch dengan quantity, expiredDate)
- ✅ Menerima `productId` (filter produk)
- ✅ Menerima `neededQty` (dalam BASE UNIT)
- ✅ Menghasilkan `Allocation[]` (batchId, take, remaining, costPrice)
- ✅ Pure function — input sama → output selalu sama
- ✅ Zero side effect
- ✅ Testable tanpa mock

### Alternatives Considered
Tidak ada alternatif. FEFO sudah pure dan akan tetap pure. ADR ini bersifat **konfirmasi** bahwa arsitektur FEFO saat ini SUDAH BENAR dan tidak boleh diubah.

### Consequences

**Positive:**
1. FEFO bisa di-test dengan unit test sederhana (input array → output array)
2. FEFO bisa digunakan oleh modul manapun tanpa dependency
3. FEFO tidak terpengaruh oleh perubahan UI/state management
4. FEFO bisa di-extract ke library terpisah di masa depan

**Constraint:**
1. FEFO tidak boleh menambah parameter baru yang berasal dari React/Zustand context
2. FEFO tidak boleh throw error yang bergantung pada UI state
3. Jika butuh data tambahan (misal: lokasi rak untuk FEFO dengan location priority), tambahkan sebagai parameter — jangan akses store

## ADR-004: Pricing sebagai Bounded Context Terpisah

### Status
**ACCEPTED** — Approved by Architecture Board + Product Owner, 2026-07-05. Architecture Governance v1.0.

### Context
Pricing saat ini (V9) dihitung secara inline di beberapa tempat:
- `use-demo-cashier.ts`: `snapshotPrice = allocationSnapshot?.[0]?.sellingPrice`
- `cashier-store.ts`: `cart.reduce((s, i) => s + i.quantity * i.unitPrice, 0)`
- `page.tsx`: `formatCurrency(item.quantity * item.unitPrice)`

Tidak ada pricing engine terpusat. Setiap komponen menghitung harga sendiri-sendiri.

### Problem
Tanpa Pricing Context terpisah, setiap penambahan aturan pricing memerlukan perubahan di BANYAK file:

**Skenario masa depan yang memerlukan Pricing Context:**

| Skenario | Aturan | Tanpa Context | Dengan Context |
|----------|--------|---------------|----------------|
| **Promo** | Diskon 10% untuk produk tertentu | Ubah 3+ file | Ubah PricingEngine saja |
| **Member Price** | Harga khusus member (5% off) | Ubah 3+ file | Tambah rule di PricingEngine |
| **BPJS** | Harga obat BPJS (regulated price) | Ubah 3+ file | Tambah PricingStrategy |
| **Dokter** | Harga resep dokter (margin berbeda) | Ubah 3+ file | Tambah PricingStrategy |
| **Dynamic Pricing** | Harga berubah berdasarkan waktu (peak/off-peak) | Ubah banyak file | Tambah TimeBasedPricing |
| **Grosir** | Diskon quantity (beli 10 gratis 1) | Ubah banyak file | Tambah QuantityDiscount |
| **Bundling** | Paket A + B = harga khusus | Tidak mungkin tanpa engine | Composition pricing |
| **Loyalty Points** | Tukar poin dengan diskon | Tidak mungkin tanpa engine | PointsRedemption rule |

### Decision
**Pricing menjadi Bounded Context tersendiri dengan PricingEngine sebagai entry point tunggal.**

```
┌─────────────────────────────────────────┐
│         PRICING BOUNDED CONTEXT          │
├─────────────────────────────────────────┤
│                                          │
│  PricingEngine (stateless)               │
│  ├── calculate(allocation, rules)        │
│  │                                       │
│  PricingRules (pluggable)                │
│  ├── StandardPricing                     │
│  ├── PromoPricing                        │
│  ├── MemberPricing                       │
│  ├── BPJSPricing                         │
│  ├── WholesalePricing                    │
│  └── CompositePricing (multi-rule)       │
│                                          │
│  PriceSnapshot (output)                  │
│  ├── Per-batch price breakdown           │
│  ├── Discount breakdown                  │
│  ├── Tax breakdown                       │
│  └── Grand total                         │
│                                          │
│  Money Policy (shared kernel)            │
│  └── normalizeRupiah()                   │
│                                          │
└─────────────────────────────────────────┘
```

### Alternatives Considered

| Alternative | Description | Verdict |
|-------------|-------------|---------|
| **A: Inline pricing (current)** | Setiap komponen hitung sendiri | **Rejected** — Tidak scalable. 3+ file harus diubah untuk setiap aturan baru |
| **B: Pricing utility function** | Satu fungsi `calculatePrice(item)` | **Rejected** — Terlalu sederhana. Tidak mendukung multi-rule, discount stacking |
| **C: Pricing di Inventory Context** | Harga sebagai bagian dari Inventory | **Rejected** — Inventory tidak peduli promo/member/discount |
| **D: Pricing Bounded Context** | Context terpisah dengan engine dan rules | **Selected** |

### Rejected Alternatives — Detail

**Rejected A (Inline Pricing):**
- Alasan ditolak: Duplikasi logic di banyak tempat. `cartTotal` dihitung di 3 tempat berbeda dengan cara berbeda
- Konsekuensi: Setiap bug pricing harus diperbaiki di semua tempat. Inconsistency antar komponen

**Rejected B (Utility Function):**
- Alasan ditolak: Tidak cukup untuk menangani aturan bisnis kompleks. Discount stacking tidak bisa dengan satu fungsi
- Konsekuensi: Function akan membengkak dengan if-else untuk setiap aturan baru

**Rejected C (Pricing in Inventory):**
- Alasan ditolak: Inventory adalah tentang stok, bukan harga jual. Inventory tahu cost price (HPP), bukan selling price akhir setelah diskon
- Konsekuensi: Inventory Store menjadi lebih besar, melanggar SRP

### Consequences

**Positive:**
1. Single entry point untuk semua perhitungan pricing
2. Rules pluggable — tambah aturan baru tanpa ubah engine
3. Testable — setiap rule bisa di-test independen
4. Audit trail — PriceSnapshot menyimpan harga pada titik waktu tertentu
5. Composite pattern — multiple rules bisa di-stack (member + promo + BPJS)

**Negative:**
1. Lebih kompleks dari inline pricing
2. Perlu strategy pattern untuk rules
3. Rule priority harus ditentukan (mana yang applied duluan?)

**Mitigation:**
- Mulai dengan StandardPricing saja (V10.3) — belum ada promo/BPJS
- Rules ditambahkan bertahap sesuai kebutuhan bisnis
- CompositePricing dengan priority order yang terdokumentasi

## ADR-005: Evolutionary Refactor vs Big Bang Refactor

### Status
**ACCEPTED** — Tidak bisa ditawar. Wajib Evolutionary.

### Context
Refactor dari V9 ke V10 melibatkan perubahan di 6+ file termasuk checkout flow yang KRITIS. Setiap bug di checkout = kehilangan uang.

### Problem
Big Bang Refactor (semua diubah sekaligus, lalu deploy) memiliki risiko:
1. **Semua atau tidak sama sekali** — jika satu bagian gagal, seluruh refactor gagal
2. **Sulit di-debug** — banyak perubahan sekaligus, sulit mencari sumber bug
3. **Tidak ada fallback** — jika produksi bermasalah, harus rollback seluruhnya (kehilangan semua progress)
4. **Testing surface besar** — harus test seluruh flow sekaligus
5. **Mental barrier** — "refactor besar-besaran" menakutkan, cenderung ditunda

### Decision
**Semua perubahan mengikuti Evolutionary (Strangler Fig) Pattern.**

```
Minggu 1-2 (V10.2): AllocationBuilder
  ┌──────────────────────────────────┐
  │ OLD: inline FEFO di hook         │ ◄── Masih jalan
  │ NEW: AllocationBuilder.build()   │ ◄── Jalan paralel
  │ TEST: output harus identik       │
  └──────────────────────────────────┘

Minggu 3-4 (V10.3): PricingEngine + Validator
  ┌──────────────────────────────────┐
  │ OLD: inline pricing di hook      │ ◄── Masih jalan
  │ NEW: PricingEngine.calculate()   │ ◄── Jalan paralel
  │ TEST: grandTotal harus identik   │
  └──────────────────────────────────┘

Minggu 5-6 (V10.4): CheckoutSession + Freezer
  ┌──────────────────────────────────┐
  │ OLD: finalizeTransaction mono    │ ◄── Masih jalan  
  │ NEW: CheckoutSessionService      │ ◄── Wraps old logic
  │ TEST: full E2E checkout          │
  └──────────────────────────────────┘

Minggu 7+ (V11.0): Cleanup
  ┌──────────────────────────────────┐
  │ REMOVE: legacy code              │ ◄── Setelah new path stabil
  │ REMOVE: dual-write compat        │
  │ REMOVE: deprecated fields        │
  └──────────────────────────────────┘
```

### Keuntungan Evolutionary Refactor

| Keuntungan | Penjelasan |
|------------|------------|
| **Low Risk** | Setiap sprint hanya ubah 1-3 file. Jika gagal, rollback kecil |
| **Backward Compatibility** | Dual-write memastikan old code tetap jalan. Consumer tidak terpengaruh |
| **Incremental Rollout** | Bisa deploy V10.2 ke production tanpa V10.3. Fitur tetap jalan |
| **Easy Rollback** | Rollback per sprint, bukan seluruh refactor. Max cost: 1-3 jam |
| **Parallel Validation** | Old dan new jalan bersamaan. Bandingkan output. Confidence tinggi |
| **Continuous Delivery** | Tidak ada "flag day" dimana semua harus deploy bersamaan |
| **Reduced Mental Load** | Developer fokus 1 domain per sprint. Kualitas lebih tinggi |

### Alternatives Considered

| Alternative | Description | Verdict |
|-------------|-------------|---------|
| **A: Big Bang Refactor** | Semua diubah sekaligus dalam 1 sprint besar | **Rejected** — Risiko terlalu tinggi untuk jalur kritis |
| **B: Feature Flag Refactor** | New code di belakang feature flag, rollout bertahap | **Rejected (untuk sekarang)** — Overhead infrastruktur feature flag tidak sebanding untuk 4 sprint |
| **C: Branch-based Refactor** | Refactor di branch terpisah, merge setelah selesai semua | **Rejected** — Merge conflict nightmare. Main branch terus berubah |
| **D: Evolutionary Refactor** | Incremental per sprint, dual-write, gradual removal | **Selected** |

### Rejected Alternatives — Detail

**Rejected A (Big Bang):**
- Alasan ditolak: Checkout adalah critical path. Big bang di checkout = potensi kehilangan transaksi
- Contoh kegagalan: "Refactor checkout selama 3 minggu. Merge. Deploy. Semua checkout error. Rollback 3 minggu progress."

**Rejected B (Feature Flag):**
- Alasan ditolak: Terlalu banyak overhead untuk 4 sprint. Feature flag service perlu di-setup, di-maintain, di-cleanup
- Bisa dipertimbangkan untuk V11+ jika skala refactor lebih besar

**Rejected C (Branch-based):**
- Alasan ditolak: Branch hidup selama 6 minggu. Main branch berubah setiap hari. Merge conflict besar di akhir
- Risiko: Resolve conflict salah → bug di production

### Consequences

**Positive:**
1. Setiap sprint deliverable — V10.2 sendiri sudah memberi nilai (allocation terpisah)
2. Rollback granular — tidak perlu mundur semua
3. Tim bisa parallel — satu orang kerjakan V10.2, yang lain review V10.3
4. Stakeholder confidence — lihat progress bertahap, bukan "tunggu 2 bulan"

**Negative:**
1. Total waktu lebih lama (8 minggu vs 3 minggu big bang)
2. Legacy code hidup lebih lama (dual-write selama 8 minggu)
3. Testing overhead — harus test old + new + dual-write

**Mitigation:**
- Dual-write dihapus setelah 1 sprint stabil (bukan menunggu semua selesai)
- Test comparison diotomatisasi (`expect(new).toEqual(old)`)
- Code review fokus pada menghilangkan dual-write secepat mungkin

# REVISI 2: ARCHITECTURE INVARIANTS

> **Status**: ADDED by Architecture Board Review — 2026-07-05
> **Definition**: Invariant adalah aturan permanen yang TIDAK BOLEH DILANGGAR oleh implementasi manapun. Setiap pelanggaran terhadap invariant adalah DEFECT dan harus diperbaiki sebelum merge.

---

## Invariant 1: Cart Tidak Boleh Mengetahui Inventory

**Penjelasan**: Cart adalah UI state untuk menampung pilihan produk kasir. Cart tidak peduli bagaimana stok dikelola, batch mana yang tersedia, atau apakah FEFO digunakan. Cart hanya menyimpan "APA yang dibeli" bukan "DARI MANA stoknya".

**Contoh Benar**:
```typescript
// ✅ CartItem hanya data minimal
const cartItem = {
  productId: "demo-001",
  baseQuantity: 10,         // Canonical — base unit
  selectedUnitCode: "strip", // Display preference
  note: "Untuk Ibu Ani",    // Optional
};
```

**Contoh Pelanggaran**:
```typescript
// ❌ CartItem tahu batch inventory
const cartItem = {
  productId: "demo-001",
  batchId: "bat-001b",       // ← VIOLATION: Cart tahu batch
  availableStock: 60,        // ← VIOLATION: Cart tahu stok
  fefoOrder: 2,              // ← VIOLATION: Cart tahu FEFO
};
```

**Dampak Jika Dilanggar**:
1. Setiap perubahan inventory schema = ubah CartItem type
2. Cart tidak bisa digunakan oleh modul non-inventory
3. Test Cart memerlukan mock inventory
4. Cart tidak bisa di-serialize tanpa inventory context

---

## Invariant 2: Allocation Tidak Boleh Mengetahui Pricing

**Penjelasan**: Allocation menjawab "batch mana yang diambil, berapa banyak". Pricing menjawab "berapa harganya". Dua pertanyaan berbeda. Dua domain berbeda.

**Contoh Benar**:
```typescript
// ✅ AllocationDraft — murni alokasi
const allocation = {
  entries: [{
    batchId: "bat-001b",
    allocatedQty: 10,         // Base unit quantity
    allocationOrder: 1,       // FEFO priority
  }],
  totalAllocated: 10,
};
```

**Contoh Pelanggaran**:
```typescript
// ❌ Allocation mengandung harga
const allocation = {
  entries: [{
    batchId: "bat-001b",
    allocatedQty: 10,
    sellingPrice: 15000,      // ← VIOLATION: Allocation tahu harga
    discount: 500,            // ← VIOLATION: Allocation tahu diskon
    subtotal: 145000,         // ← VIOLATION: Allocation tahu subtotal
  }],
};
```

**Dampak Jika Dilanggar**:
1. Perubahan aturan diskon = rebuild allocation (tidak perlu)
2. Allocation tidak bisa digunakan untuk transfer stok (karena membawa harga)
3. Allocation tidak bisa digunakan untuk opname (karena membawa diskon)
4. Single Responsibility Principle violation

---

## Invariant 3: Pricing Tidak Boleh Mengakses FEFO

**Penjelasan**: Pricing tidak peduli bagaimana batch dipilih. Pricing hanya peduli "batch X allocated Q — berapa harganya?". Urutan FEFO tidak relevan untuk kalkulasi harga.

**Contoh Benar**:
```typescript
// ✅ PricingEngine menerima AllocationDraft (hasil FEFO), bukan menjalankan FEFO
function calculatePricing(allocation: AllocationDraft, batches: Batch[]): PriceSnapshot {
  // Lookup price dari batch yang sudah dialokasikan
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ PricingEngine menjalankan FEFO sendiri
function calculatePricing(productId: string, qty: number, batches: Batch[]): PriceSnapshot {
  const fefoResult = allocateFefo(batches, productId, qty);  // ← VIOLATION
  // ...
}
```

**Dampak Jika Dilanggar**:
1. Pricing harus tahu aturan FEFO (expiry date comparison)
2. Perubahan aturan FEFO (misal: FEFO + location priority) harus ubah Pricing
3. Pricing tidak bisa di-test tanpa data batch lengkap dengan expiry

## Invariant 4: Checkout Hanya Boleh Melalui CheckoutSession

**Penjelasan**: Tidak boleh ada jalan pintas. Setiap operasi checkout (allocate, price, validate, freeze) harus melalui CheckoutSession. Tidak boleh allocate langsung, tidak boleh freeze langsung.

**Contoh Benar**:
```typescript
// ✅ Semua melalui CheckoutSessionService
const session = checkoutService.createSession(cart);
const draft = await checkoutService.allocateInventory(session);
const priced = await checkoutService.calculatePricing(session, draft);
const validated = await checkoutService.validate(session);
const frozen = await checkoutService.freeze(session);
```

**Contoh Pelanggaran**:
```typescript
// ❌ Jalan pintas — bypass CheckoutSession
const allocations = allocateFefo(batches, productId, qty);  // ← VIOLATION
const price = allocations[0].batch.sellingPrice;             // ← VIOLATION
inventoryRepo.deductStock(allocations);                      // ← VIOLATION
transactionRepo.createTransaction({...});                    // ← VIOLATION
```

**Dampak Jika Dilanggar**:
1. Tidak ada lifecycle — tidak bisa tahu state checkout saat ini
2. Rollback sulit — operasi parsial tanpa koordinasi
3. Duplikasi logic — setiap jalan pintas mengulang logic yang sama
4. Tidak ada audit trail — siapa yang allocate? kapan?

## Invariant 5: Transaction Menjadi Immutable Setelah Freeze

**Penjelasan**: Begitu TransactionFreezer.freeze() dipanggil, TransactionSnapshot TIDAK BOLEH diubah. Tidak ada update. Tidak ada delete. Tidak ada soft-delete. Immutable selamanya.

**Contoh Benar**:
```typescript
// ✅ TransactionSnapshot — semua field readonly
interface TransactionSnapshot {
  readonly snapshotId: string;
  readonly frozenAt: string;    // ISO8601 — waktu freeze
  readonly items: readonly FrozenTransactionItem[];
  readonly payments: readonly FrozenPayment[];
  readonly total: number;
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ Transaction bisa diubah setelah freeze
transaction.total = 50000;           // ← VIOLATION
transaction.items.push(newItem);     // ← VIOLATION
transaction.payments[0].amount = 0;  // ← VIOLATION
```

**Dampak Jika Dilanggar**:
1. Audit trail tidak bisa dipercaya — transaksi bisa berubah setelah selesai
2. Laporan keuangan tidak akurat — total berubah setelah closing
3. Fraud risk — kasir bisa mengubah transaksi setelah customer pergi
4. Reconciliation impossible — data berubah terus

## Invariant 6: Receipt Hanya Membaca TransactionSnapshot

**Penjelasan**: Receipt (struk) hanya membaca data dari TransactionSnapshot yang sudah immutable. Receipt TIDAK BOLEH membaca Cart aktif, Allocation, atau Inventory untuk menghasilkan struk.

**Contoh Benar**:
```typescript
// ✅ Receipt membaca dari TransactionSnapshot
function generateReceipt(snapshot: TransactionSnapshot): ReceiptData {
  return {
    invoiceNumber: snapshot.invoiceNumber,
    items: snapshot.items,
    total: snapshot.total,
    // ...
  };
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ Receipt membaca dari Cart aktif
function generateReceipt(): ReceiptData {
  const cart = useCashierStore.getState().cart;  // ← VIOLATION
  const total = cart.reduce(...);                 // ← VIOLATION
}
```

**Dampak Jika Dilanggar**:
1. Struk bisa berbeda dengan transaksi yang tersimpan
2. Jika cart sudah di-clear, struk tidak bisa dicetak ulang
3. Receipt tidak bisa dirender dari history (hanya dari session aktif)

## Invariant 7: Inventory Merupakan Single Source of Truth untuk Stok

**Penjelasan**: Hanya ada SATU tempat yang menyimpan data stok: Inventory (batches[] di inventory-store, yang bersumber dari database via inventoryRepo). Tidak boleh ada copy stok di Cart, CheckoutSession, atau komponen UI.

**Contoh Benar**:
```typescript
// ✅ Stok hanya dibaca dari Inventory melalui Repository
const batches = await inventoryRepo.getBatchesByProduct(productId);
const totalStock = batches.reduce((s, b) => s + b.quantity, 0);
```

**Contoh Pelanggaran**:
```typescript
// ❌ Stok di-copy ke CartItem
const cartItem = {
  productId: "demo-001",
  stockAvailable: 100,  // ← VIOLATION: Copy stok di Cart
};
```

**Dampak Jika Dilanggar**:
1. Stok di Cart bisa stale (tidak update setelah transaksi lain)
2. Overselling — Cart pikir stok 100, padahal sudah berkurang
3. Dua source of truth — mana yang benar?

## Invariant 8: AllocationDraft Tidak Boleh Dipersist sebagai Histori Transaksi

**Penjelasan**: AllocationDraft adalah draft — bisa berubah, bisa di-rebuild. Yang disimpan sebagai histori adalah `sale_batch_allocations` (database) dan TransactionSnapshot (immutable). AllocationDraft adalah objek sementara selama checkout session.

**Contoh Benar**:
```typescript
// ✅ Yang disimpan ke database adalah hasil freeze
await saleAllocationRepo.record(transactionSnapshot);
```

**Contoh Pelanggaran**:
```typescript
// ❌ AllocationDraft disimpan sebagai histori
localStorage.setItem('allocation-history', JSON.stringify(allocationDraft));  // ← VIOLATION
```

**Dampak Jika Dilanggar**:
1. Histori bisa berisi data yang tidak valid (draft yang di-rebuild)
2. Tidak bisa membedakan draft dan transaksi final
3. Storage terisi data sampah (draft yang tidak jadi checkout)

## Invariant 9: FEFO Hanya Menerima Base Unit

**Penjelasan**: FEFO engine beroperasi pada BASE UNIT (satuan terkecil: tablet, kapsul, mL). FEFO tidak menerima "1 Dus" atau "3 Strip". Konversi display unit → base unit harus dilakukan SEBELUM memanggil FEFO.

**Contoh Benar**:
```typescript
// ✅ Konversi ke base unit dulu, baru FEFO
const baseQty = toBaseUnit(1, "Dus", unitLevels);  // 1 Dus = 200 Tablet
const allocation = allocateFefo(batches, productId, baseQty);  // FEFO dalam Tablet
```

**Contoh Pelanggaran**:
```typescript
// ❌ FEFO menerima display unit
const allocation = allocateFefo(batches, productId, 1, "Dus");  // ← VIOLATION
```

**Dampak Jika Dilanggar**:
1. FEFO harus tahu unit conversion — melanggar single responsibility
2. Konversi unit berbeda antar produk (1 Dus bisa 10 Strip atau 20 Strip)
3. FEFO tidak bisa dibandingkan antar produk dengan unit berbeda

---

## Invariant 10: Semua Domain Service Harus Stateless

**Penjelasan**: AllocationBuilder, PricingEngine, AllocationValidator, TransactionFreezer — semuanya STATELESS. Tidak boleh menyimpan state internal. Tidak boleh memiliki cache. Tidak boleh memiliki counter. Input sama → output selalu sama.

**Contoh Benar**:
```typescript
// ✅ Pure function — stateless
function buildAllocation(input: AllocationInput): AllocationDraft {
  const { batches, productId, neededQty } = input;  // Semua dari parameter
  // ...
  return allocationDraft;
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ Domain service dengan state internal
let lastAllocationTime: number = 0;  // ← VIOLATION: State
let allocationCache = new Map();      // ← VIOLATION: Cache

function buildAllocation(input: AllocationInput): AllocationDraft {
  const cached = allocationCache.get(input.productId);  // ← VIOLATION
  if (cached) return cached;
  // ...
}
```

**Dampak Jika Dilanggar**:
1. Non-deterministic — hasil berbeda untuk input yang sama (cache hit vs miss)
2. Test tidak reliabel — state dari test sebelumnya mempengaruhi test berikutnya
3. Tidak bisa parallel — state sharing antar concurrent calls

---

## Invariant 11: Branch Isolation Tidak Boleh Dilewati

**Penjelasan**: Setiap transaksi terjadi dalam konteks branch tertentu. Data inventory adalah branch-specific. CheckoutSession harus membawa branchId dan semua operasi harus di-scope ke branch tersebut. Tidak boleh ada transaksi lintas branch.

**Contoh Benar**:
```typescript
// ✅ Branch context selalu disertakan
const session = checkoutService.createSession(cart, {
  branchId: "branch-001",
  tenantId: "tenant-001",
});
const batches = await inventoryRepo.getBatches({ branchId: session.branchId });
```

**Contoh Pelanggaran**:
```typescript
// ❌ Query inventory tanpa branch filter
const batches = await inventoryRepo.getBatches();  // ← VIOLATION: Tanpa branch scope
```

**Dampak Jika Dilanggar**:
1. Data leak — cabang A melihat stok cabang B
2. Double sell — stok yang sama dijual oleh dua cabang berbeda
3. Tenant isolation breach — potensi lihat data tenant lain

## Invariant 12: Repository Tidak Boleh Dipanggil Langsung dari React Component

**Penjelasan**: React Component hanya boleh mengakses Application Layer (hooks, services). Tidak boleh langsung memanggil `inventoryRepo.getBatches()` atau `transactionRepo.createTransaction()`. Semua akses data harus melalui service/hook.

**Contoh Benar**:
```typescript
// ✅ Component memanggil hook
function CashierPage() {
  const { demoProducts } = useDemoCashier();  // Hook → Service → Repository
  // ...
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ Component memanggil Repository langsung
function CashierPage() {
  useEffect(() => {
    inventoryRepo.getBatches().then(setBatches);  // ← VIOLATION
    transactionRepo.getTransactions().then(setTxns);  // ← VIOLATION
  }, []);
}
```

**Dampak Jika Dilanggar**:
1. Component bergantung pada implementasi Repository
2. Tidak bisa ganti Repository tanpa ubah Component
3. Test Component harus mock Repository
4. Clean Architecture layer violation

## Invariant 13: Semua Domain Service Harus Deterministic

**Penjelasan**: Untuk input yang sama, domain service harus menghasilkan output yang sama — SELALU. Tidak boleh bergantung pada `Date.now()`, `Math.random()`, atau external state.

**Contoh Benar**:
```typescript
// ✅ Semua input eksplisit — deterministic
function calculatePricing(
  allocation: AllocationDraft,
  batches: Batch[],
  rules: PricingRule[],
  pricingDate: string,  // ← Explicit, bukan Date.now()
): PriceSnapshot { ... }
```

**Contoh Pelanggaran**:
```typescript
// ❌ Bergantung pada waktu sistem
function calculatePricing(allocation: AllocationDraft): PriceSnapshot {
  const now = Date.now();  // ← VIOLATION: Non-deterministic
  if (now > PROMO_END_DATE) { ... }
}
```

**Dampak Jika Dilanggar**:
1. Test flaky — hasil berbeda tergantung jam berapa test dijalankan
2. Snapshot tidak reproducible — tidak bisa bandingkan hasil antar environment
3. Debug sulit — hasil berubah-ubah tanpa perubahan input

---

## Invariant 14: Pricing Engine Tidak Boleh Mengubah Stok

**Penjelasan**: PricingEngine hanya MEMBACA data batch untuk lookup harga. PricingEngine TIDAK BOLEH menulis, mengurangi, atau mengubah quantity batch.

**Contoh Benar**:
```typescript
// ✅ PricingEngine hanya membaca
function calculatePricing(allocation: AllocationDraft, batches: Batch[]): PriceSnapshot {
  const price = batches.find(b => b.id === entry.batchId)?.sellingPrice;  // READ ONLY
  // ...
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ PricingEngine mengurangi stok
function calculatePricing(allocation: AllocationDraft, batches: Batch[]): PriceSnapshot {
  batches.find(b => b.id === entry.batchId)!.quantity -= entry.allocatedQty;  // ← VIOLATION
}
```

**Dampak Jika Dilanggar**:
1. Stok berkurang sebelum transaksi final (masih bisa cancel)
2. Stok berkurang dua kali — PricingEngine + InventoryEngine
3. Pricing side effect — sulit di-test, sulit di-debug

## Invariant 15: Inventory Engine Tidak Boleh Menghitung Profit

**Penjelasan**: Inventory Engine (FEFO, deductStock) berurusan dengan stok — quantity, batch, expiry. Inventory tahu `costPrice` (HPP) tapi tidak menghitung profit. Profit = sellingPrice - costPrice — itu domain Finance/Reporting.

**Contoh Benar**:
```typescript
// ✅ Inventory mencatat cost price untuk HPP, bukan profit
interface StockMovement {
  type: "sale";
  qtyChange: -10;
  costPrice: 8000;  // ← Untuk HPP calculation nanti, bukan profit sekarang
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ Inventory menghitung profit
function deductForSale(...) {
  const profit = (sellingPrice - costPrice) * quantity;  // ← VIOLATION
  this.totalProfit += profit;                             // ← VIOLATION
}
```

**Dampak Jika Dilanggar**:
1. Profit calculation duplikasi — Inventory dan Reporting hitung sendiri-sendiri
2. Angka profit berbeda antar modul — mana yang benar?
3. Inventory Store membesar dengan concern finance

## Invariant 16: Receipt Tidak Boleh Membaca Cart Aktif

**Penjelasan**: Receipt hanya dari TransactionSnapshot (lihat Invariant 6). Lebih spesifik: Receipt TIDAK BOLEH membaca `useCashierStore.getState().cart`. Cart adalah UI state sementara. Receipt adalah output permanen.

**Contoh Benar**:
```typescript
// ✅ Receipt dari TransactionSnapshot
function ReceiptPreview({ transactionId }: { transactionId: string }) {
  const snapshot = useTransactionSnapshot(transactionId);
  return <Receipt data={snapshot} />;
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ Receipt membaca Cart
function ReceiptPreview() {
  const cart = useCashierStore(s => s.cart);  // ← VIOLATION
  const total = cart.reduce(...);             // ← VIOLATION
}
```

**Dampak Jika Dilanggar**:
1. Receipt tidak bisa ditampilkan setelah cart di-reset
2. Receipt tidak bisa dicetak ulang dari history transaksi
3. Isi receipt bisa berbeda dengan transaksi di database

## Invariant 17: Frozen Transaction Tidak Boleh Dimodifikasi

**Penjelasan**: Ini memperkuat Invariant 5. Setelah TransactionFreezer.freeze(), tidak ada operasi yang boleh mengubah TransactionSnapshot. Tidak ada update quantity. Tidak ada adjustment harga. Tidak ada hapus item. Jika ada kesalahan, buat transaksi koreksi BARU (reversal/invoice revision).

**Contoh Benar**:
```typescript
// ✅ Koreksi lewat transaksi baru (Invoice Revision)
function correctTransaction(originalTxnId: string, corrections: Correction[]) {
  return correctionEngine.createRevision(originalTxnId, corrections);
  // Membuat transaksi BARU dengan reference ke original
}
```

**Contoh Pelanggaran**:
```typescript
// ❌ Mengubah transaksi yang sudah frozen
function fixTransaction(txnId: string, newTotal: number) {
  const txn = await transactionRepo.findById(txnId);
  txn.total = newTotal;                   // ← VIOLATION
  await transactionRepo.update(txn);      // ← VIOLATION
}
```

**Dampak Jika Dilanggar**:
1. Audit trail tidak valid — transaksi berubah setelah selesai
2. Laporan keuangan tidak bisa di-audit
3. Regulasi — apotek diwajibkan menyimpan record transaksi yang akurat dan tidak berubah

## Invariant 18: Semua Perubahan Stok Harus Berasal dari Inventory Engine

**Penjelasan**: Tidak boleh ada kode yang langsung mengubah `batch.quantity` kecuali melalui Inventory Engine (FEFO deduction, purchase receipt, stock opname, write-off). Komponen UI, Cart, CheckoutSession, PricingEngine — tidak boleh menyentuh quantity.

**Contoh Benar**:
```typescript
// ✅ Perubahan stok melalui Inventory
await inventoryRepo.deductStock(allocations);  // ← Dedicated method
await inventoryRepo.addStock(purchaseItems);   // ← Dedicated method
await inventoryRepo.adjustStock(opnameDiffs);  // ← Dedicated method
```

**Contoh Pelanggaran**:
```typescript
// ❌ Langsung ubah batch quantity
batch.quantity -= 10;                           // ← VIOLATION
await supabase.from("product_batches").update({  // ← VIOLATION
  quantity: batch.quantity,
}).eq("id", batch.id);
```

**Dampak Jika Dilanggar**:
1. Stock movement tidak tercatat — audit trail rusak
2. Tidak ada validasi — quantity bisa negatif tanpa terdeteksi
3. Concurrent update race condition — dua operasi ubah quantity bersamaan
4. HPP calculation rusak — tidak tahu kapan dan kenapa stok berubah

## 5.4 God Object Prevention Rules

Untuk mencegah CheckoutSession berkembang menjadi God Object:

1. **Jika suatu method tidak mengakses state internal CheckoutSession, method tersebut bukan milik CheckoutSession** — pindahkan ke Domain Service terpisah.

2. **Jika suatu data tidak berubah sepanjang lifecycle session, data tersebut bukan milik session** — cukup referensi (FK).

3. **Jika suatu operasi bisa dijalankan tanpa session (pure function dari input → output), operasi tersebut adalah Domain Service** — bukan method CheckoutSession.

4. **CheckoutSession hanya boleh punya SATU alasan untuk berubah**: perubahan pada lifecycle checkout.

5. **Jika menambah field baru ke CheckoutSession, tanyakan**: "Apakah field ini berubah sepanjang lifecycle? Apakah field ini adalah inti dari proses checkout?" Jika jawaban tidak, jangan tambahkan.

# REVISI 6: REPOSITORY ABSTRACTION CONFIRMATION

> **Status**: ADDED by Architecture Board Review — 2026-07-05
> **Purpose**: Memastikan Domain Layer tidak bergantung pada implementasi Repository. Menerapkan Dependency Inversion Principle.

---

## 6.1 The Problem with Direct Repository Dependency

```typescript
// ❌ Domain bergantung pada implementasi konkrit
// src/lib/cashier/allocation-builder.ts
import { inventoryRepo } from "@/lib/repository-instances";  // ← VIOLATION

function buildAllocation(productId: string, neededQty: number): AllocationDraft {
  const batches = await inventoryRepo.getBatches();  // ← Domain calls Repository directly
  // ...
}
```

**Masalah**:
1. AllocationBuilder tidak bisa di-test tanpa mock `inventoryRepo`
2. AllocationBuilder tidak bisa digunakan di environment tanpa Supabase
3. Jika implementasi Repository berubah, AllocationBuilder harus berubah
4. Tidak bisa ganti Inventory Repository dengan implementasi berbeda (in-memory, REST API, gRPC)

---

## 6.2 The Solution: Repository Interface (Dependency Inversion)

```typescript
// ✅ Domain mendefinisikan INTERFACE yang dibutuhkan
// src/lib/cashier/types.ts

/** Contract yang dibutuhkan AllocationBuilder dari Infrastructure */
interface BatchProvider {
  getBatchesByProduct(productId: string): ProductBatch[];
  getBatchById(batchId: string): ProductBatch | undefined;
}

/** Contract yang dibutuhkan PricingEngine dari Infrastructure */
interface BatchPriceProvider {
  getSellingPrice(batchId: string): number;
  getCostPrice(batchId: string): number;
}

/** Contract yang dibutuhkan Validator dari Infrastructure */
interface InventorySnapshotProvider {
  getCurrentBatches(productId: string): ProductBatch[];
}

/** Contract yang dibutuhkan Freezer dari Infrastructure */
interface InventoryDeductionProvider {
  deductStock(allocations: AllocationEntry[]): Promise<void>;
}

/** Contract yang dibutuhkan Freezer dari Infrastructure */
interface TransactionPersistenceProvider {
  createTransaction(snapshot: TransactionSnapshot): Promise<Transaction>;
  recordAllocations(snapshot: TransactionSnapshot): Promise<void>;
}
```

## 6.4 Service Wiring (Dependency Injection)

```typescript
// ✅ Application Layer melakukan wiring
// src/services/checkout-session.service.ts

interface CheckoutSessionDependencies {
  batchProvider: BatchProvider;              // ← Interface, bukan implementasi
  priceProvider: BatchPriceProvider;         // ← Interface
  inventoryProvider: InventorySnapshotProvider; // ← Interface
  deductionProvider: InventoryDeductionProvider; // ← Interface
  transactionProvider: TransactionPersistenceProvider; // ← Interface
}

class CheckoutSessionService {
  constructor(private deps: CheckoutSessionDependencies) {}
  
  async allocateInventory(session: CheckoutSession): Promise<AllocationDraft> {
    // Domain service tidak tahu ini Supabase, REST, atau in-memory
    const batches = this.deps.batchProvider.getBatchesByProduct(session.productId);
    return buildAllocation({ productId: session.productId, neededQty: session.baseQty, batches });
  }
}

// ─── Wiring di startup ───
const service = new CheckoutSessionService({
  batchProvider: new InventoryBatchProvider(),
  priceProvider: new InventoryPriceProvider(),
  inventoryProvider: new InventorySnapshotProvider(),
  deductionProvider: new InventoryDeductionAdapter(),
  transactionProvider: new TransactionPersistenceAdapter(),
});
```

# ARCHITECTURE PRINCIPLES

> **Status**: ADDED — Architecture Board — 2026-07-05
> **Purpose**: Prinsip fundamental yang menjadi filosofi utama arsitektur MEDISYNC

---

## Principle 1 — Single Source of Truth (SSOT)

```
Setiap data hanya memiliki SATU tempat penyimpanan yang authoritative.
Tidak boleh ada copy, cache, atau derived state yang menjadi acuan.
```

**Penerapan di MEDISYNC**:
- Inventory adalah SSOT untuk stok — Cart tidak menyimpan stok
- CheckoutSession adalah SSOT untuk state checkout — komponen tidak menyimpan state checkout sendiri
- TransactionSnapshot adalah SSOT untuk transaksi final — receipt tidak menyimpan copy
- Money Policy (`normalizeRupiah`) adalah SSOT untuk nilai Rupiah — tidak ada `Math.round()` di tempat lain

**Rasional**: Tanpa SSOT, data yang sama bisa memiliki nilai berbeda di tempat berbeda. Debug menjadi sangat sulit. "Stok di Cart 100, tapi di Inventory 95 — mana yang benar?"

---

## Principle 2 — Immutable Transaction

```
Setelah transaksi dibekukan (freeze), data tidak boleh berubah.
Koreksi dilakukan dengan membuat transaksi baru, bukan mengubah yang lama.
```

**Penerapan di MEDISYNC**:
- `TransactionSnapshot` — immutable setelah `TransactionFreezer.freeze()`
- Koreksi melalui Invoice Revision (transaksi koreksi baru)
- Tidak ada UPDATE pada transaksi yang sudah completed
- Audit trail selalu lengkap karena tidak ada data yang berubah

**Rasional**: Di industri farmasi/apotek, integritas transaksi adalah keharusan regulasi. Transaksi yang bisa diubah setelah selesai = fraud risk + audit failure.

---

## Principle 3 — Pure Domain Services

```
Semua Domain Service harus pure function.
Input sama → output selalu sama. Zero side effect.
```

**Penerapan di MEDISYNC**:
- `AllocationBuilder.build()` — pure, menerima `Batch[]` + `neededQty`
- `PricingEngine.calculate()` — pure, menerima `AllocationDraft` + `BatchPriceProvider`
- `FEFO Engine` — pure, sudah dari V9
- Semua Domain Service: tidak akses store, tidak akses DB, tidak akses API

**Rasional**: Pure function testable tanpa mock. Tidak ada "berhasil di development, gagal di production" karena external state berbeda. Parallel execution aman.

---

## Principle 4 — Stateless Domain Logic

```
Domain Service tidak boleh menyimpan state internal.
Tidak boleh memiliki cache, counter, atau mutable field.
```

**Penerapan di MEDISYNC**:
- `AllocationBuilder`, `PricingEngine`, `Validator`, `Freezer` — semuanya stateless
- State hanya di Aggregate Root (`CheckoutSession`) dan UI Store (`Cart`)
- Domain Service menerima semua data sebagai parameter eksplisit

**Rasional**: Stateful service = hidden bug. "Kenapa hasilnya berbeda padahal inputnya sama?" — karena ada state internal yang berubah. Stateless = predictable.

---

## Principle 5 — Dependency Inversion

```
Domain Layer mendefinisikan interface.
Infrastructure Layer mengimplementasi.
High-level policy tidak bergantung pada low-level detail.
```

**Penerapan di MEDISYNC**:
- `AllocationBuilder` butuh batch → definisikan `BatchProvider` interface
- `PricingEngine` butuh harga → definisikan `BatchPriceProvider` interface
- Infrastructure (`inventoryRepo`, `transactionRepo`) mengimplementasi interface tersebut
- Domain tidak import `supabase`, `zustand`, `@/store/*`

**Rasional**: Jika implementasi database berubah (Supabase → PostgreSQL langsung), domain logic tidak perlu diubah. Hanya adapter yang berubah.

---

## Principle 6 — Composition over Coupling

```
Bangun fungsionalitas dengan mengkomposisi domain service,
bukan dengan meng-coupling modul satu sama lain.
```

**Penerapan di MEDISYNC**:
- `CheckoutSessionService` mengkomposisi: `AllocationBuilder` → `PricingEngine` → `Validator` → `Freezer`
- Setiap domain service independen — bisa di-test sendiri-sendiri
- Pricing tidak import Allocation. Allocation tidak import Pricing.
- Mereka dikomposisi oleh Application Layer, bukan saling memanggil

**Rasional**: Coupling = perubahan di satu tempat memaksa perubahan di tempat lain. Composition = setiap bagian independen, bisa di-swap, di-test, di-reuse.

---

## Principle 7 — Evolutionary Refactoring

```
Tidak ada Big Bang. Perubahan dilakukan bertahap, inkremental.
Old code dan new code hidup berdampingan selama transisi.
```

**Penerapan di MEDISYNC**:
- V10.2: Ekstrak Allocation → dual-write
- V10.3: Ekstrak Pricing → dual-write
- V10.4: Orchestration → old code dihapus setelah new code stabil
- Rollback per sprint, bukan seluruh program

**Rasional**: Big Bang = "mengerjakan 3 bulan, deploy, gagal, rollback 3 bulan". Evolutionary = "deploy setiap 2 minggu, kalau gagal rollback 1 sprint". Checkout adalah critical path — tidak boleh ada "hari tanpa checkout".

---

## Principle 8 — Explicit State Machine

```
Setiap lifecycle yang memiliki state transition harus dieksplisitkan.
Tidak boleh ada state implisit. Tidak boleh ada transisi ilegal.
```

**Penerapan di MEDISYNC**:
- `CheckoutSession` memiliki 6 state eksplisit: `DRAFT → ALLOCATING → PRICED → VALIDATED → FROZEN → CANCELLED`
- Transisi ilegal ditolak: tidak bisa `DRAFT → FROZEN` (harus melalui `ALLOCATING`, `PRICED`, `VALIDATED`)
- Setiap state tahu operasi apa yang diizinkan

**Rasional**: State implisit = "kenapa bisa freeze padahal belum validasi?" Explicit state machine = compiler/type system bisa memverifikasi transisi.

---

## Principle 9 — Repository Abstraction

```
Domain tidak boleh tahu implementasi data access.
Semua akses data melalui interface yang didefinisikan Domain.
```

**Penerapan di MEDISYNC**:
- `BatchProvider` interface (Domain) → `InventoryBatchProvider` implementasi (Infrastructure)
- `TransactionPersistenceProvider` interface (Domain) → `TransactionPersistenceAdapter` (Infrastructure)
- Domain tidak import Supabase client
- Test menggunakan fake provider, production menggunakan real provider

**Rasional**: Tanpa abstraction, setiap test harus mock Supabase. Setiap perubahan database = ubah domain. Dengan abstraction, test pakai in-memory provider, production pakai Supabase provider.

---

## Principle 10 — Backward Compatibility

```
Setiap perubahan harus backward-compatible.
Consumer tidak boleh broken karena perubahan internal.
```

**Penerapan di MEDISYNC**:
- Dual-write: data ditulis ke old format + new format
- Legacy fields dipertahankan sampai consumer dimigrasi
- CartItem masih memiliki field legacy (`quantity`, `unitPrice`) sampai V11.0
- Tipe baru ditambahkan tanpa menghapus tipe lama

**Rasional**: Backward-incompatible change = "satu tim refactor, semua tim lain harus ikut berubah". Backward-compatible = "tim cashier refactor, tim inventory/reporting tidak terpengaruh".

# ARCHITECTURE GLOSSARY

## Core Domain Concepts

| Term | Definition |
|------|------------|
| **CheckoutSession** | Aggregate Root yang mengelola seluruh lifecycle checkout — dari DRAFT hingga FROZEN. Satu-satunya entry point untuk operasi checkout. Memiliki 6 state: DRAFT, ALLOCATING, PRICED, VALIDATED, FROZEN, CANCELLED |
| **Aggregate Root** | Entity utama dalam sebuah aggregate DDD yang menjadi gatekeeper untuk semua operasi terhadap aggregate tersebut. Semua akses ke child entities/value objects harus melalui Aggregate Root. Dalam konteks V10: CheckoutSession |
| **AllocationDraft** | Value Object yang merepresentasikan hasil alokasi FEFO — batch mana yang diambil, berapa quantity. Bersifat mutable (draft, bisa di-rebuild). TIDAK mengandung harga, diskon, atau pajak |
| **PriceSnapshot** | Value Object yang merepresentasikan hasil kalkulasi harga pada suatu titik waktu — selling price, discount, tax, subtotal, grand total. Immutable terhadap perubahan allocation (harus di-recalculate jika allocation berubah) |
| **ValidationResult** | Value Object hasil validasi AllocationDraft terhadap kondisi inventory terkini. Status: VALID (bisa lanjut freeze) atau INVALID (perlu rebuild, disertai ChangeSet) |
| **TransactionSnapshot** | Value Object immutable yang merepresentasikan transaksi yang sudah di-freeze. Berisi seluruh data yang diperlukan untuk receipt, audit, dan reporting. Setelah freeze, TIDAK BOLEH diubah |
| **AllocationBuilder** | Domain Service (stateless) yang membangun AllocationDraft dari ProductBatch[] menggunakan FEFO engine. Input: Batch[] + neededQty. Output: AllocationDraft |
| **PricingEngine** | Domain Service (stateless) yang menghitung PriceSnapshot dari AllocationDraft + batch price data. Mendukung multiple pricing rules (standard, promo, member, BPJS) melalui strategy pattern |
| **TransactionFreezer** | Domain Service (stateless) yang membekukan CheckoutSession menjadi TransactionSnapshot immutable. Operasi final dalam lifecycle checkout |

---

## Engine & Algorithm

| Term | Definition |
|------|------------|
| **FEFO** | First Expired, First Out — algoritma prioritas pengambilan stok berdasarkan tanggal kadaluarsa. Batch dengan expiredDate terdekat diambil terlebih dahulu. Pure function — tidak memiliki side effect atau dependency eksternal |
| **FEFO Engine** | Implementasi pure function dari algoritma FEFO. Menerima ProductBatch[], mengembalikan allocation. Sudah pure di V9, tetap pure di V10. Berlokasi di `src/lib/inventory-demo.ts` (akan tetap di sana) |
| **Money Policy** | Shared kernel untuk normalisasi dan validasi nilai Rupiah. Semua monetary value wajib melalui `normalizeRupiah()`. Lihat `src/lib/money/normalize-rupiah.ts` |
| **UUCE** | Universal Unit Conversion Engine — engine konversi satuan bertingkat. Mengelola konversi Base Unit ↔ Display Unit. Lihat `src/lib/uuce/` |

---

## Architecture Layers

| Term | Definition |
|------|------------|
| **Presentation Layer** | Lapisan terluar — React Components, UI rendering. HANYA boleh bergantung pada Application Layer. Contoh: `src/app/(tenant)/cashier/page.tsx`, `src/components/cashier/` |
| **Application Layer** | Lapisan orkestrasi — hooks, services. Mengkoordinasi Domain Services dan Infrastructure. Tidak mengandung business logic. Contoh: `src/hooks/use-demo-cashier.ts`, `src/services/checkout-session.service.ts` |
| **Domain Layer** | Lapisan inti — business logic, domain services, value objects. TIDAK BOLEH bergantung pada Infrastructure. Contoh: `src/lib/cashier/allocation-builder.ts`, `src/lib/cashier/pricing-engine.ts` |
| **Infrastructure Layer** | Lapisan terbawah — database, API, external services, repositories. Mengimplementasi interface yang didefinisikan Domain. Contoh: `src/lib/repositories/`, `src/lib/supabase/` |

---

## DDD Concepts

| Term | Definition |
|------|------------|
| **Bounded Context** | Batas logis sebuah domain model. Setiap context memiliki model, bahasa, dan aturan sendiri. Konteks dalam MEDISYNC: Cashier, Inventory, Pricing, Product, Audit, Reporting |
| **Domain Event** | Kejadian penting dalam domain yang memicu reaksi dari komponen lain. Contoh: `CartChanged`, `AllocationBuilt`, `PricingCalculated`, `TransactionFrozen` |
| **Value Object** | Objek immutable yang diidentifikasi oleh nilainya, bukan ID. Tidak memiliki lifecycle sendiri. Contoh: `AllocationDraft`, `PriceSnapshot`, `TransactionSnapshot` |
| **Repository** | Pattern untuk memisahkan domain logic dari data access. Domain mendefinisikan interface; Infrastructure mengimplementasi. Contoh: `BatchProvider` (interface), `InventoryBatchProvider` (implementation) |

---

## Process & Lifecycle

| Term | Definition |
|------|------------|
| **Freeze** | Operasi final dalam lifecycle CheckoutSession. Mengubah session status menjadi FROZEN dan menghasilkan TransactionSnapshot immutable. Setelah freeze: tidak boleh ada perubahan apapun |
| **Dual Write** | Strategi migrasi evolutionary: menulis data ke dua path (old + new) secara paralel selama masa transisi. Old path tetap jalan. New path divalidasi. Setelah stabil, old path dihapus |
| **Evolutionary Refactor** | Pendekatan refactoring bertahap (strangler fig pattern). Setiap sprint mengekstrak satu domain. Tidak ada Big Bang. Old code dan new code hidup berdampingan selama transisi |
| **Architecture Invariant** | Aturan permanen yang TIDAK BOLEH dilanggar. Setiap pelanggaran adalah DEFECT. Ada 18 invariant dalam blueprint ini. Perubahan invariant hanya bisa melalui Architecture Board Review |

---

## Governance

| Term | Definition |
|------|------------|
| **Architecture Decision Record (ADR)** | Dokumen formal yang merekam keputusan arsitektur — konteks, problem, alternatif, keputusan, konsekuensi. 5 ADR dalam V10.1 |
| **Architecture Governance** | Aturan dan prosedur untuk mengelola perubahan arsitektur. Menentukan apa yang boleh diubah tanpa review, apa yang wajib melalui Architecture Board |
| **Architecture Board** | Tim yang bertanggung jawab atas integritas arsitektur. Meng-approve perubahan arsitektur, mereview compliance, menjaga invariant |
| **Architecture Baseline** | Versi arsitektur yang sudah disetujui dan menjadi acuan resmi. Blueprint V10.1 adalah Architecture Baseline pertama MEDISYNC |
| **Fitness Checklist** | Daftar periksa untuk memvalidasi kepatuhan arsitektur sebelum sprint dinyatakan APPROVED. Mencakup Dependency Rules, Invariants, dan Domain Service purity |

## Change Classification

|------|-----------------|

| **Architecture Decision Records** | Menambah ADR baru. Membatalkan ADR existing. Mengubah decision |

Perubahan berikut boleh dilakukan **tanpa** Architecture Board Review:

| Area | Contoh Perubahan |
|------|-----------------|
| **Internal Refactoring** | Extract method, rename variable, simplify logic — tanpa mengubah contract |

| **Unit Test** | Menambah test case, improve coverage, fix flaky test |
| **Bug Fix** | Memperbaiki bug yang TIDAK memerlukan perubahan arsitektur |
| **Documentation** | Memperbaiki comment, update README, tambah JSDoc |
| **Rename Variable** | Rename local variable, parameter — tanpa mengubah API publik |
| **Comment** | Tambah/hapus/ubah komentar — tanpa mengubah perilaku |
| **Formatting** | Prettier, ESLint fix, whitespace — tanpa logika berubah |
| **Error Message** | Memperbaiki teks error, tambah konteks — tanpa mengubah handling |
| **Logging** | Tambah log, ubah log level — tanpa mengubah flow |

```
  ▼
Tentukan kategori (A atau B)
  │
  ├── Kategori B → Langsung implementasikan
  │
  └── Kategori A → Lanjut ke ACR Process:
       │
       ├─ 1. Developer menulis ACR dengan format:
       │     - Change description
       │     - Current architecture
       │     - Proposed change
       │     - Rationale
       │     - Impact analysis
       │     - Affected ADRs, Invariants, Rules
       │
       ├─ 2. Architecture Board review (maks 48 jam)
       │     - Review kelengkapan ACR
       │     - Analisis dampak
       │     - Diskusi dengan developer jika perlu
       │
       ├─ 3. Architecture Board Decision:
       │     ├── APPROVED → Lanjut ke step 4
       │     ├── REVISION NEEDED → Kembali ke step 1 dengan feedback
       │     └── REJECTED → Ditutup dengan alasan tertulis
       │
       ├─ 4. Blueprint diperbarui dalam 24 jam
       │     - ADR baru jika diperlukan
       │     - Update section terkait
       │     - Governance version dinaikkan
       │
       └─ 5. Developer di-notify — implementasi boleh dimulai
```

## Emergency Change Procedure

Untuk situasi darurat (production down, critical bug yang memerlukan bypass arsitektur):

1. **Bypass diizinkan** — dengan persetujuan minimal 1 Architecture Board member
2. **Document the bypass** — tulis ACR retrospektif dalam 24 jam
3. **Time-boxed** — bypass berlaku maks 5 hari kerja
4. **Proper fix required** — setelah emergency, implementasi yang sesuai arsitektur harus menggantikan bypass

## Policy Compliance

| Kebijakan | Konsekuensi Pelanggaran |
|-----------|------------------------|
| Category A change tanpa Board Review | **BLOCKER** — PR tidak bisa di-merge. Change di-revert |
| Category A change setelah ditolak Board | **BLOCKER** — Harus di-revert. Developer wajib konsultasi |
| Blueprint tidak diperbarui setelah ACR approved | **MAJOR** — Sprint tidak bisa di-APPROVED sampai blueprint up-to-date |
| Emergency bypass tanpa dokumentasi | **MAJOR** — ACR retrospektif wajib dalam 24 jam |
