### Transitions

| From | To | Trigger | Guard |
|------|----|---------|-------|
| EMPTY | IMPORTING | User clicks [Import] / [New Draft] | None |
| IMPORTING | PARSING | File uploaded / form submitted | File size < 10MB, row count < 500 |
| IMPORTING | EMPTY | User cancels before upload | None |
| PARSING | VALIDATING | Parse complete | At least 1 row parsed |
| PARSING | HAS_ERROR | All rows failed to parse | 0 valid rows |

| VALIDATING | HAS_ERROR | Critical validation failures | Missing required fields |
| MATCHING PRODUCTS | WARNING ANALYSIS | All items matched or flagged | At least 1 item matched |
| MATCHING PRODUCTS | HAS_ERROR | No items could be matched | All items unmatched |
| WARNING ANALYSIS | READY | 0 warnings | — |
| WARNING ANALYSIS | HAS_WARNING | Warnings found | — |
| WARNING ANALYSIS | HAS_ERROR | Critical errors | — |
| HAS_WARNING | USER REVIEW | User opens draft | Warnings acknowledged |
| HAS_ERROR | USER REVIEW | User opens draft | Errors must be resolved |
| READY | USER REVIEW | User opens draft | Optional review |
| USER REVIEW | CONFIRM | User clicks [Konfirmasi] | All items resolved, 0 errors |
| USER REVIEW | SAVE DRAFT | User clicks [Simpan Draft] | None |
| USER REVIEW | CANCEL | User clicks [Batal] | None |
| CONFIRM | addPurchase() | Draft validated | 0 errors, all items matched |
| CONFIRM | HAS_ERROR | Validation fails at confirm | FK errors, missing data |
| SAVE DRAFT | DRAFT SAVED | Draft persisted | — |
| CANCEL | CANCELLED | Draft discarded | None |
| addPurchase() | COMPLETED | Existing engine success | — |
| addPurchase() | HAS_ERROR | Existing engine failure | addPurchase threw |

## STEP 2 — PURCHASE DRAFT STATUSES

### Draft-Level Statuses

```ts
type DraftStatus =
  | "draft"         // Initial — just created, not yet validated
  | "validating"    // Currently running validation
  | "matching"      // Currently running product matching
  | "ready"         // All items validated, no warnings, no errors
  | "has_warning"   // Validated, but has warnings (prices, dates, etc.)
  | "has_error"     // Has errors — cannot be confirmed
  | "confirmed"     // Admin confirmed → pushed to existing engine
  | "completed"     // Transaction saved successfully
  | "cancelled"     // Discarded
```

### Status Behavior

| Status | Can Edit? | Can Confirm? | Can Cancel? | Description |
|--------|-----------|-------------|-------------|-------------|
| `draft` | ✅ | ❌ | ✅ | Fresh draft, needs validation |
| `validating` | ❌ | ❌ | ❌ | Validation running (async) |
| `matching` | ❌ | ❌ | ❌ | Product matching running |
| `ready` | ✅ | ✅ | ✅ | Clean — ready to confirm |
| `has_warning` | ✅ | ✅ | ✅ | Warnings exist but don't block |
| `has_error` | ✅ | ❌ | ✅ | Requires manual resolution |
| `confirmed` | ❌ | ❌ | ❌ | Being processed |
| `completed` | ❌ | ❌ | ❌ | Terminal — done |
| `cancelled` | ❌ | ❌ | ❌ | Terminal — discarded |

### Status Colors (UI)


## STEP 3 — PURCHASE ITEM STATUSES

### Item-Level Statuses

```ts
type DraftItemStatus =
  | "pending"       // Not yet processed
  | "matched"       // Product matched (exact)
  | "fuzzy_match"   // Product matched (fuzzy, confidence < 100%)
  | "unmatched"     // No product found
  | "warning"       // Has warnings (price, date, etc.)
  | "error"         // Has errors (invalid data)
  | "merged"        // Merged into another item
  | "deleted"       // Removed by user
```

### Status Transitions (per item)

```
pending ──→ matched (barcode/exact name match)
       │
       ├─→ fuzzy_match (similar name, confidence 70-99%)
       │
       ├─→ unmatched (no match, confidence < 70%)
       │
       └─→ error (validation failed)

matched ──→ warning (price anomaly, date warning)

fuzzy_match ──→ matched (user confirmed match)
            │
            ├─→ unmatched (user rejected match)
            │
            └─→ warning

unmatched ──→ matched (user chose product)
          │
          └─→ matched (user created new product)

warning ──→ matched (user acknowledged)

error ──→ pending (user fixed data)

matched ──→ merged (consolidated into another item)
matched ──→ deleted (user removed item)
```

| Status | Edit | Delete | Rematch | Create New | Merge |

## STEP 4 — MATCH ENGINE DESIGN

### Matching Priority (highest → lowest)

```
┌─────────────────────────────────────────────────────────────┐
│ 1. BARCODE EXACT                                            │
│    products.barcode = input.barcode                         │
│    → confidence: 100%, method: "barcode"                    │
├─────────────────────────────────────────────────────────────┤
│ 2. PRODUCT CODE EXACT                                       │
│    products.code = input.product_code                       │
│    → confidence: 100%, method: "code"                       │
├─────────────────────────────────────────────────────────────┤
│ 3. NAME EXACT (normalized)                                  │
│    normalize(input.name) = normalize(product.name)           │
│    → strip case, special chars, extra spaces                │
│    → confidence: 100%, method: "exact"                      │
├─────────────────────────────────────────────────────────────┤
│ 4. NAME TOKEN MATCH                                         │
│    All tokens in input appear in product name (or vice versa)│
│    Example: "Paracetamol 500" ↔ "Paracetamol 500mg IFARS"   │
│    → confidence: 85-95%, method: "token_match"              │
├─────────────────────────────────────────────────────────────┤
│ 5. FUZZY SIMILARITY (Levenshtein)                           │
│    distance < 3 AND input length > 5                        │
│    → confidence: 70-84%, method: "fuzzy"                    │
├─────────────────────────────────────────────────────────────┤
│ 6. NO MATCH                                                 │
│    Nothing above threshold                                  │
│    → confidence: 0%, method: "unmatched"                    │
└─────────────────────────────────────────────────────────────┘
```

### Confidence Thresholds

```
┌───────────┬──────────┬──────────┬─────────────────┐
│  SCORE    │  BADGE   │  AUTO?   │  ACTION         │
├───────────┼──────────┼──────────┼─────────────────┤
│ 100%      │ 🟢 EXACT │ ✅       │ No review       │
│ 90–99%    │ 🟢 HIGH  │ ✅       │ Quick glance    │
│ 80–89%    │ 🟡 MED   │ ⚠️       │ Review suggested│
│ 70–79%    │ 🟠 LOW   │ ❌       │ Review required │
│ 1–69%     │ 🔴 NONE  │ ❌       │ Manual match    │
│ 0%        │ ⚪ NONE  │ ❌       │ Create new      │
└───────────┴──────────┴──────────┴─────────────────┘
```

### Normalization Function

```ts
function normalizeName(name: string): string {
  return name
    .toLowerCase()
    .replace(/[^a-z0-9\s]/g, '')  // remove special chars
    .replace(/\s+/g, ' ')          // collapse spaces
    .trim();
}
```

### Rule: NO automatic product creation

The match engine NEVER creates products automatically. Unmatched items must be:
- Manually matched by admin, OR
- Admin creates new product via QuickCreateProductModal

## STEP 7 — SAVE DRAFT DESIGN

### Persistence Strategy

```
Draft State
  │
  ├── Zustand Store (in-memory)
  │   └── Survives: SPA navigation
  │   └── Lost on: full page refresh, tab close
  │
  └── localStorage (backup)
      └── Survives: page refresh, tab close
      └── Lost on: browser clear, private mode exit
      └── Key: purchaseDraft_{draftId}
      └── Max: 5 drafts per user
```

### Draft Store

```ts
interface PurchaseDraftStore {
  drafts: PurchaseDraft[];            // all drafts for current user
  activeDraftId: string | null;       // currently open draft

  createDraft: (source: DraftSource) => string;
  loadDraft: (id: string) => PurchaseDraft | null;
  saveDraft: (draft: PurchaseDraft) => void;
  deleteDraft: (id: string) => void;
  archiveDraft: (id: string) => void;
  restoreFromLocalStorage: () => void;
}
```

### Draft Lifecycle with Persistence

```
Create → Save (localStorage) → Close browser → Reopen → Restore from localStorage
   │                                                                    │
   └──────────────────── Draft survives ────────────────────────────────┘
```

### Auto-Cleanup

| Condition | Action |
|-----------|--------|
| Draft.status = "completed" | Remove from localStorage after 24 hours |
| Draft.status = "cancelled" | Remove from localStorage after 7 days |
| Draft.status = "draft" (stale) | Remove after 30 days of no updates |
| Draft count > 5 | Delete oldest cancelled draft |

## STEP 8 — RECOVERY FLOW

### Scenario: Browser Closed Mid-Import

```
1. User starts CSV import → 50 rows parsed → browser crashes
2. User reopens browser → logs in → navigates to Purchasing
3. System detects: localStorage has draft with status="draft"
   and items.length > 0 but status ≠ "completed"
4. Toast: "Draft pembelian sebelumnya ditemukan. Lanjutkan?" [Ya] [Hapus]
5. User clicks [Ya] → draft restored → back to REVIEW step
```

### Scenario: Tab Crash During Review

```
1. User in REVIEW with 30 items → tab crashes
2. Every item edit triggers auto-save to localStorage (debounced, 2s)
3. On reload: restore draft from localStorage
4. Draft state: exactly as last auto-save
5. Lost: at most 2 seconds of unsaved edits
```

### Scenario: Network Lost During Confirm

```
1. User clicks [Konfirmasi] → addPurchase() called
2. Network drops → Supabase call times out after 10s
3. addPurchase() throws → caught → draft.status = "has_error"
4. Error message: "Gagal menyimpan pembelian: network timeout. Coba lagi."
5. Draft preserved — user can retry
6. Duplicate prevention: cart hash check (same as cashier duplicate prevention)
```

### Scenario: Refresh During Import

```
1. User starts Excel import → beforeunload event fires
2. Dialog: "Import sedang berjalan. Yakin ingin meninggalkan halaman?"
3. If user proceeds: localStorage auto-saves current draft state
4. On return: draft restored from localStorage
```

### Recovery States Summary

| Scenario | Data Loss | Recovery |
|----------|-----------|----------|
| Browser close | Max 2s of edits | Auto-restore from localStorage |
| Tab crash | Max 2s of edits | Auto-restore from localStorage |
| Network drop | 0 (draft preserved) | Retry confirm |
| Refresh during import | 0 (intercepted) | beforeunload dialog |
| Power loss | Max 2s of edits | Auto-restore from localStorage |

## STEP 10 — RISK ANALYSIS

| Risk | Severity | Likelihood | Mitigation |
|------|----------|------------|------------|
| Wrong product match (fuzzy) causes wrong stock deduction | HIGH | MEDIUM | Confidence threshold 85%+ for auto-accept; manual review for all fuzzy matches |
| Duplicate purchase (same draft confirmed twice) | HIGH | LOW | Confirmation gate checks draft.status !== "completed"; cart hash dedup |
| Draft lost on browser crash before auto-save | MEDIUM | LOW | Auto-save every 2 seconds; beforeunload handler |
| Large draft (500 items) slows UI | MEDIUM | LOW | Pagination (50 items/page); virtual scroll |
| Stale draft with deleted product | MEDIUM | LOW | Validate all product IDs at confirmation gate |
| Merge logic miscalculates weighted price | LOW | LOW | Display calculation preview before merge |
| localStorage full (5MB limit) | LOW | VERY LOW | Max 5 drafts × ~2KB each = 10KB total |
